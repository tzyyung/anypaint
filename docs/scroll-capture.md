# 滾動截圖：功能與做法

**這是滾動截圖的單一事實來源**：功能行為、架構、演算法、參數、效能數字、驗證方式，
以及 §9「不要改回去」的收斂清單，全部在這裡。程式碼與這份不符時**以程式碼為準並立刻修這份**。

`CLAUDE.md` 只放跨功能的通用規範（合成測資紀律、AppKit／ScreenCaptureKit 陷阱、
不憑印象寫 API⋯），**不重複本文的內容**——兩邊各記一份必然漂移，已經發生過。
`docs/superpowers/specs/` 下的設計文件是「當初為什麼這樣決定」的歷史快照，不是現況。

最後更新：2026-07-27

## 1. 使用者看到的行為

`⌘⇧X` → 拉框圈住會捲動的內容 → 按「開始」或直接在框內滾一下 → 自己往下捲 →
捲到底自動結束（或按「完成」）→ 預覽視窗可複製（⌘C）／存檔（⌘S）／另存（⇧⌘S）／
存檔並開啟（⌘O）／丟棄。
（「存檔並開啟」＝存到快速儲存路徑後交給外部 App（設定 → 輸出 → 開啟方式，未指定＝系統
預設的圖片程式）；長圖本身沒有內建標註，這是它的替代路徑。）

| 行為 | 說明 |
|---|---|
| 啟動 | 明確按「開始」，或選區內第一個滾輪事件（手動／自動都相容） |
| 進度 | HUD 顯示已拼接像素數；捲太快會提示放慢或回捲 |
| 回捲 | 往上捲會**同步撤回**長圖尾端（不是拼進去） |
| 到底 | 自動判定收尾；只在該次品質有疑慮時才請使用者回捲確認 |
| 停滯收工 | 12 秒完全無進展才收工（**不可用「連續失敗次數」**——30fps 下連續 10 格只有 1/3 秒，手一甩超出可匹配範圍就被強制結束，來不及依提示回捲救回） |
| 固定區域 | 頁首／頁尾／捲軸欄自動偵測並裁除 |
| 頁面自捲 | 延遲載入的內容會拼進去 |
| 局部動畫 | 廣告／loading spinner 等原地變動**不會**被誤當成捲動 |
| 取消 | Esc（selecting/armed）、HUD 取消鈕、再按 ⌘⇧X、看門狗逾時 |
| 最小選區 | 高 320 **像素**（Retina 約 160 點） |

限制：需 macOS 14+；一次只能拼一個選區；螢幕由**滑鼠所在位置**決定。

## 2. 資料流

```
⌘⇧X
 └─ ScrollCaptureSession（@MainActor，狀態機協調者，不做演算法）
     ├─ ScrollSelectionOverlay   拉框選區
     ├─ ScrollHUD                進度與引導訊息（文案）
     ├─ ScrollGuidance           該說什麼話的決策（純邏輯）
     ├─ ScrollFrameSource        SCStream 供格（30fps，只在畫面變動時供）
     └─ engineQueue（序列佇列，背景）
         └─ ScrollStitchEngine   影格消化：軌跡＋匹配＋拼接
             ├─ ScrollMatcher      位移估計（純邏輯）
             ├─ ScrollTrajectory   時間軌跡（純邏輯）
             ├─ StaticBandDetector 靜態帶偵測（純邏輯）
             └─ ScrollStitcher     長圖 buffer（純邏輯）
 └─ ScrollPreviewWindow          結束後的預覽

PixelBuffer.swift  共用型別：PixelBuffer / LumaPlane / BandInsets / ScrollCoords（座標鏈）
ScrollCaptureSelfCheck.swift  自檢工具（見 §7），不參與正式流程
```

**分層原則**：`ScrollMatcher` / `ScrollTrajectory` / `StaticBandDetector` / `ScrollStitcher` /
`ScrollGuidance` 與 `PixelBuffer.swift` 裡的型別都不碰 AppKit 也不碰 SCStream，
所以能在 `anypaint-selftest` 用合成影格端到端驗證。
engine 也不碰 UI；session 只負責「誰在什麼時候呼叫誰」。

## 3. 每格的處理流程

```
consume(frame)
 ├─ ① 影像指紋 gate：抽樣 2048 點比對上一次處理過的格
 │     畫面完全沒變 → waitingForMotion（不計失敗）
 │
 ├─ ② 步進估計 matchStep(new, 上一格)          ← 對「上一格」而非長圖尾端
 │     ├─ 高信心 dy≈0 → noMotion（局部動畫，跳過，不進救援層）
 │     ├─ 有位移      → trajectory.recordStep(dy)
 │     └─ 估不出      → 依速度推測一格（連續上限 2 格）
 │
 ├─ ③ 軌跡累積量 < minDelta(14px) → waitingForMotion（等，基準是固定的長圖尾端，不漏內容）
 │
 ├─ ④ 主匹配：以軌跡預測位移為 prior，對長圖尾端做原解析度 ZNCC
 │     ├─ dy > 0 → append
 │     ├─ dy < 0 → cropTail（回捲撤回）
 │     └─ 失敗   → ⑤
 │
 └─ ⑤ 救援（**順序有意義，不可對調**）
       ├─ a. Vision 全圖對位（獨立第二意見，必經 matcher 複核）
       ├─ b. 步進估不出**且**速度推測額度已用盡 → rejected（HUD 提示回捲）
       │     這一關必須排在 c/d 前面：此時 pendingDy 全部來自推測、不可信，
       │     拿它去等待或外推只會把錯誤內容拼進長圖。
       ├─ c. 軌跡還有餘裕 → awaitingOverlap（等下一格，不猜）
       └─ d. 再等會失去重疊 → 依軌跡外推接上，標記 appendedApproximate
```

## 4. 三個核心設計決定

### 4.1 位移只由影像決定，滾輪只表達使用者意圖

| 用途 | 資料來源 |
|---|---|
| 位移量、方向、符號 | **只能是影像**（步進估計的結果，含正負號） |
| 「開始」的啟動訊號 | 滾輪事件 |
| 「到底」判定（還在捲但畫面不動） | 滾輪事件（此時畫面不供格，影像無從得知） |
| 軌跡異常的交叉檢查 | 滾輪趨勢，**僅寫診斷、不改行為** |

滾輪的 `scrollingDeltaY` 尺度隨裝置差異極大，而且使用者可能用捲軸拖曳、鍵盤 Page Down、
或頁面自己捲動——那些完全沒有滾輪事件。**但**「使用者還在嘗試捲、畫面卻不動」是到底的唯一
可觀測訊號（畫面靜止時 SCStream 不供格），那是輸入事件的正當用途。

兩條證據流的交叉驗證表：

| 滾輪 | 影像 | 判定 | 行為 |
|---|---|---|---|
| 有 | 變化＋匹配成功 | 正常捲動 | append |
| 有 | 變化＋匹配不到 | 捲太快 | 提示放慢或回捲 |
| 有 | 無變化 | 疑似到底 | 自動收尾；有疑慮才要求回捲確認 |
| 無 | 變化 | 頁面自捲／動畫 | 由步進估計區分（見 4.3） |
| 無 | 無變化 | 停手 | 等待（看門狗） |

### 4.2 影格序列是時間序列（軌跡）

「對長圖尾端」的位移大、搜尋範圍大，等行距內容的週期解就落在範圍內；
「對上一格」的位移小、重疊 95% 以上，歧義幾乎為零。所以先解容易的題目：

1. **步進估計**對上一格估位移（L1 解析度＋拋物線次像素插值）
2. **軌跡累積**成預測位移，當主匹配的 prior，搜尋窗縮到 ±12px（週期解進不了窗）
3. 寫進長圖的位移**永遠**由對長圖尾端的原解析度全列 ZNCC 裁決

第 3 點是 drift 不會累積進長圖的原因：軌跡只縮小搜尋窗。這是文獻上 video mosaicing 的
pairwise＋校正組合；只做 pairwise 串接才會 drift。

`ScrollTrajectory` 的兩個關鍵語意：
- `commit(actualDy:)` **扣除**已接部分而非歸零——差額可能是「還沒接上的內容」而非誤差；
  只有小於 `minDelta` 的餘額才當 drift 清掉。
- `mustCommitNow(maxDy:)` 問的是「**再等一格**會不會超過上限」，不是「現在有沒有超過」。

### 4.3 「有信心的 0」與「估不出」必須分開

`StepOutcome` 刻意分兩種：

- `.step(dy: 0, ...)`＝**有信心地**確認畫面在變但沒有一致平移 → 局部動畫，安全跳過
- `.unknown`＝估不出 → 該格仍必須進救援層

混為一談會把真實捲動的內容當成動畫丟掉，違反「完整性優先於接縫完美」的產品裁決。

## 5. 匹配演算法

### 5.1 計分：整個重疊區的 ZNCC

`overlapScore(new:ref:dy:)` 對整個重疊區算零均值正規化互相關，回 `(mean, worst)`：
- `mean`：全重疊區的 1−ZNCC。ZNCC 已正規化，不同大小的重疊可公平比較。
- `worst`：重疊區切四等分取最差的一份，抓局部污染（影片區、動態元件）；
  只看有足夠訊號的區塊，否則低紋理區塊的雜訊會誤判成污染。

**`worst` 只有兩處品質閘用得到，但它等於把重疊區再掃一遍**，所以所有「找最佳位移」的
掃描迴圈都要傳 `needsWorst: false`（實測這一項就讓 matchStep 從 16.7ms 降到 9.1ms）。

取樣的兩個方向**不對稱**：垂直位移的資訊在**水平邊緣**（文字行的上下緣、分隔線），
所以加大 `colStep` 只是少看幾欄、不損失垂直鑑別力；加大 `rowStep` 則會跳過細橫線而失配
（實測 rowStep=2 讓「大片純色＋一條 3px 細線」直接失配）。要省成本就動 colStep。
但 colStep 要**隨影格寬度自適應**：選區寬度沒有下限（只有高度有 320px 門檻），
細長框上固定 colStep=4 會讓每列只剩十幾個取樣點。

去均值後平坦區對分子分母貢獻都趨零——既不冒充相關，也不壓過有紋理處。
兩邊皆平坦回 nil（無資訊），**不可**回「完美相關」。

### 5.2 主匹配：軌跡 prior 快路徑 + 全域候選複評

```
有軌跡 prior（常態）
  → L1 掃 ±6 → L0 精修 ±2 → 全列 ZNCC 複評
  → 過閘則接受；不過閘則落到下面

全域候選複評
  → L2 全域掃，收自適應候選集（分數 < best×3、間隔 > 排除窗、上限 8）
  → 每個候選在 L1 精修排序 → 只有前 2 名進 L0 全列
  → 比值閘一律在**原解析度**判定
```

兩條路徑的成本見 §7 的基準表。

粗掃層（L2）只**提名候選**，不做生死裁決——它的分數常糊在一起，而原解析度是乾淨的。

錯的 prior 不會把結果帶跑：快路徑過不了閘就自動落到全域複評（實測餵行倍數錯解或荒謬值
當 prior，仍找回正解）。

### 5.3 步進估計

在 L1（1/2 解析度）做，配拋物線三點次像素插值。搜尋窗以上次步進為中心（速度連續性），
**窗內過不了閘就退回全域掃**——使用者一改變方向，真解就落在窗外；背壓丟格時同理。
絕對品質閘 0.15 比主匹配的 0.35 嚴，因為 f2f 的重疊有 95% 以上、真匹配分數應該極低。

### 5.4 金字塔精修的餘裕與取樣精度

兩個數字是實測換來的，改小會出錯：

- **精修半徑 6**（不是 3）：每上一層放大 2 倍，前一層的 ±1~2 量化誤差會變成 ±2~4；
  半徑 3 只剩 1px 餘裕，實測會落在窗外導致 dy 差 1px。
- **最終層必須全列**（`rowStep: 1`）：隔列取樣讓分數對 ±1px 不敏感、甚至排名反轉
  （實測 dy=201 的分數比正解 dy=200 還低）。粗掃層可以隔列省成本。
  要省成本請改 `colStep`（見 §5.1 的不對稱性）。

### 5.5 靜態帶

第一次成功匹配時用兩格比對偵測四向不動的區域（頁首／頁尾／捲軸欄），鎖定後裁除。
鎖定**必須在任何 append 之前**，否則裁尾下限會被抬高而永久鎖不上。
連續 5 次偵測失敗就用 zero insets 強制鎖定，避免卡死。

## 6. 並發模型

| 元件 | 隔離 |
|---|---|
| `ScrollCaptureSession` | `@MainActor` |
| `ScrollStitchEngine` | **只在 `engineQueue`（序列）上被觸碰**，含唯讀屬性與 `finalize()` |
| 純邏輯型別 | 值型別、`Sendable` |

匹配鏈很重（debug build 單格可達 1.7 秒），放主執行緒會把計時器／HUD／事件監聽全部餓死。
所以：

- **背壓**：engine 忙碌時只保留最新一格。丟掉中間格無害——匹配基準是固定的長圖尾端，
  位移會累積到下一次一併接上。
- **狀態傳遞**：MainActor 需要的 engine 資訊一律透過 `ScrollStitchEngine.Snapshot` 帶出佇列，
  **不可直接讀 engine 屬性**。這條原本只寫在註解裡而實際被違反（MainActor 讀 `trajectory`
  寫診斷、同步呼叫 `finalize()`），而 `finalize()` 會讀 stitcher 的 buffer——快捲時按「完成」
  就會與進行中的 `consume` 競爭同一塊記憶體。
- **`finish()` 是非同步的**：`finalize()` 排進 engineQueue 才能保證接在最後一格之後。
  這開了一個「收尾中」的新窗口（舊版同步 finish 沒有），要一併處理三件事：
  ① `finish()` 一開始就停看門狗——否則逾時會走 `cancel()`，使用者拿到 nil 而**丟掉已拼好的長圖**；
  ② `cancel()` 在 `.finishing` 狀態 no-op——長圖已經拼好、只差純計算的 finalize；
  ③ 完成時再確認狀態，否則會發出第二次 `onFinished`（預覽視窗開兩個）。
- **收尾判定是 `appendedFrameCount > 1`**：初始值就是 1（基準格），寫成 `>= 1` 會恆真——
  「一格都沒拼到就靜默」的規則失效，拉框後什麼都沒捲就按完成會開一個只有單張影格的預覽視窗。

## 7. 驗證

```bash
swift run -c release anypaint-selftest        # 純邏輯（項數不記在文件裡，見 CLAUDE.md 基線紀律）
./scripts/build_app.sh release
open -n -a "$PWD/build.noindex/anypaint.app" --args --scroll-selfcheck
```

**三層驗證缺一不可**：

1. **selftest**：純邏輯。含位移估計的迴歸矩陣——稀疏度矩陣、跨內容類型
   （密集文字／深色終端機風／照片類平滑紋理）、病態內容必須拒絕、prior 抗誤導；
   以及 Snapshot 與 engine 屬性的一致性、0 格靜默、窄選區（寬度**沒有下限**）的步進準確度。
2. **app 內自檢**：真實 SCStream 擷取＋完整匹配鏈，驗證拼接量落在預期 ±10%。
   `--selfcheck-sparse=1 --selfcheck-height=186 --selfcheck-step=90` 是極端壓力情境。
   **必須 `open -n`**——既有實例會吃掉 `--args`。
3. **常駐 session 診斷**：`/tmp/anypaint-scroll-session.log`，每次真實使用都寫
   （session 起訖、選區、第一格尺寸與**平均亮度**、每格 outcome 與軌跡、收尾統計）。
   第一格的平均亮度可判定「擷取到的畫面是否與使用者眼見一致」——這條區分了
   「擷取階段」與「匹配階段」的問題，是最先該看的一行。

**自檢的三個判準紀律**（都是踩過才加的）：
- **上下界都要卡**：只設下限的話「拼太多」（重複內容）也會 PASS——曾出現 203% 報 PASS。
- **測資要真的落在選區內**（曾把文字畫在選區外 → 擷取到 100% 空白的無效情境），
  而且必須是**物理上的純平移**（見 `CLAUDE.md` 的合成測資紀律——這條讓好幾輪結論全部作廢）。
- **必須 `open -n`**：既有實例會吃掉 `--args`，症狀是「啟動了卻不寫 log」。

**驗收前務必確認測的是新版**：常駐 app 是啟動時載入映像，重建 binary 不影響已在跑的實例。
實測踩過——拿凌晨啟動的舊實例測當天中午的改動，數據完全誤導。
新版 log 每行都有 `step=` 與 `f2f累積=`，沒有這兩個欄位就是舊版在跑。

合成測試通過 ≠ 實機可用。軌跡架構的三個 bug 全是在 selftest 全綠時由實機自檢抓出來的。

**效能基準**（release，2026-07-27 量測）。成本與影格面積成正比，**不標尺寸的數字沒有意義**——
專案裡的效能數字以這張表為準，其他文件不要各自記一份：

| | 1957×736（實機） | 1485×366 |
|---|---|---|
| `matchStep`（有 prior） | 4.0 ms | 1.5 ms |
| `matchStep`（開場，無 prior） | 5.8 ms | 1.8 ms |
| `match`（軌跡 prior 快路徑） | 12.0 ms | 3.6 ms |
| `match`（全域候選複評） | 20.6 ms | 5.9 ms |
| **engine 端到端每格** | **21 ms** | 6.7 ms |

30fps 的預算是 33 ms/格；實機自檢最慢單格 27 ms。

改動熱路徑後要重量——**先用一次性 probe 量出成分再改，不要憑推理優化**。
實測推翻過「fingerprint 重複計算」「診斷字串」這兩個看似浪費的假設
（分別只有 0.001ms 與 0.008ms），真正的熱點是 `matchStep`。

診斷欄位怎麼讀：

| 欄位 | 健康 | 有問題 |
|---|---|---|
| `step=` | `step(dy: N, score: 0.0…)` | 大量 `unknown` |
| `f2f累積` vs `已提交` | 貼近 | **長期背離＝步進估計在撞假峰** |
| outcome 分佈 | 多數 `appended` | 大量 `appendedApproximate` / `rejected` |
| 收尾 `品質有疑慮=` | `false` | `true` |

**基準數據**（供日後回歸比對）：

| 情境 | 結果 |
|---|---|
| 自檢：正常密度 40 步 | 達成率 99%、最慢單格 27ms、零失敗 |
| 自檢：極端稀疏（`--selfcheck-sparse=1 --selfcheck-height=186 --selfcheck-step=90`） | 96%、零 rejected |
| **實機**：Chrome 長網頁＋深色主題（第一格平均亮度 22）、選區 978×368 點、Retina | `appended=127`、`appendedApproximate=0`、`rejected=0`、`品質有疑慮=false`、drift 0.2% |
| 對照：同機的舊架構（相位相關還在） | `appended=2 / appendedApproximate=88 / rejected=185`，使用者症狀「容易重疊」 |

實機那一列同時涵蓋**深色低對比**——那正是 band 取樣時代最嚴重的失效條件
（平坦區抹平分數曲面 → 永久 ambiguous → 長圖等於單張影格）。

## 8. 評估過但沒有採用

| 方案 | 為什麼不用 |
|---|---|
| 1-D 投影相位相關 | 四類內容各 10 組實測命中率 20%，錯時連符號都錯；而它被觸發的時機正是它最不可靠的時機。已整條移除。若要重新引入，必須做多峰複評而非取單峰。 |
| Vision 光流（`VNTrackOpticalFlowRequest`） | header 明載 "very resource intensive"；ML revision 的 magnitude 有系統性偏差（只能當 prior）；dense flow 每格 4MB 還要自己取中位數。收益只在「重疊區全空白」時顯現，且會把最低需求推到 macOS 14。 |
| 深度學習匹配（LoFTR / RAFT 等） | 解的是大視角變化與光照劇變，而本問題是純垂直平移，ZNCC 已是最優統計估計（實測 40/40 零判錯）。需自行壓縮蒸餾轉 CoreML，與極簡離線 native app 的定位不合。 |
| 離線全域最佳化（bundle adjustment） | 品質上限最高，但目前沒有證據顯示 drift 是實機問題（實測 0.2%），且要付記憶體與收尾延遲。 |
| band 取樣計分 | 三個互相牽制的坑（平坦 band 冒充完美相關、band 位置隨位移改變偏好大位移、窄寬兩難）。整區 ZNCC 一次消解。 |

真正無解的情境是「重疊區整段空白」——那是資訊不存在，任何演算法（含模型）都變不出來，
只能靠軌跡外推並明確標記。

## 9. 不要改回去（曾經試過、失敗了）

每一條都是實機或實測付出代價換來的。改這些之前先讀對應的節。

| 想改的東西 | 為什麼不能 | 詳見 |
|---|---|---|
| 用滾輪事件量判斷「有沒有在捲」 | 實機一整場 session 累積滾輪只有 3 點，卻收到 **116 格影格**（畫面一直在動）——全被 10 點門檻擋掉，一次匹配都沒跑，長圖等於單張影格。`scrollingDeltaY` 的尺度隨裝置差異極大，而且捲軸拖曳／鍵盤／頁面自捲**完全沒有滾輪事件** | §4.1 |
| 改回 band 取樣計分 | 三個坑互相牽制：平坦 band 冒充完美相關 → 永久 ambiguous；剔除平坦後 band 位置隨位移改變 → 偏好大位移（拼出 203% 重複內容）；固定位置又陷入窄／寬兩難 | §5.1 |
| 把精修半徑改小、或最終層改隔列 | 半徑 3 只剩 1px 餘裕會落在窗外；隔列讓分數對 ±1px 不敏感甚至排名反轉（dy=201 比正解 dy=200 分數還低） | §5.4 |
| 讓救援層自己決定位移 | Vision 在**完全沒有重疊**的影格上仍會給出看似合理的位移，接受後把錯誤內容永久拼進長圖。所有救援估計都必須經 matcher 以它為 prior 複核並過閘 | §3 ⑤a |
| 匹配失敗就丟格 | 稀疏內容下整段捲動內容會永久消失，使用者的感受是「捲了很多卻只看到最初框選的一小塊」。**完整性優先於接縫完美**（使用者裁決） | §3 ⑤d |
| 用「連續失敗次數」收工 | 30fps 下連續 10 格只有 1/3 秒 | §1 |
| 讓粗掃層直接判 ambiguous | L2 的分數常糊在一起（0.0460 / 0.0546，比值 1.19 剛好擦過 1.1 門檻），而原解析度是乾淨的（0.0000 / 0.0444）。用糊掉的那層決定生死 → 訊號一弱就永久放棄 | §5.2 |
| 重新引入 1-D 相位相關 | 四類內容各 10 組實測命中率 20%，錯時**連符號都錯**；而它被觸發的時機正是它最不可靠的時機。若真要引入，必須做多峰複評而非取單峰 | §8 |
| `commit` 時把預測歸零 | 位移被上限夾住時，差額是**還沒接上的真實內容**不是誤差——實測丟掉 44% 內容 | §4.2 |
| 把「該不該現在接」改成看「現在有沒有超過上限」 | 會讓 pending 翻倍後被截斷，實測卡在 83% | §4.2 |
| 拿掉步進搜尋窗的全域 fallback | 窗以上次步進為中心，使用者一改變方向真解就落在窗外 → **回捲永遠估不出** | §5.3 |
| 放寬速度推測的限制 | 與舊版造成過量 47% 的「猜速度」只有一線之隔。三個限制缺一不可：只進軌跡不直接接上、連續上限 2 格、不更新 `lastStep`（推測不可自我增強） | §3 ② |
| 在 MainActor 直接讀 engine 屬性或呼叫 `finalize()` | `finalize()` 會讀 stitcher 的 buffer，與進行中的 `consume` 競爭同一塊記憶體（快捲時按「完成」即可撞上） | §6 |
